## 硬性规则（必须遵守，违反任何一条视为失败）

### 规则 1：信息来源必须"新鲜"，禁止凑数
- **只收录今天（24 小时内）或最近 48 小时内的真实新闻、论文、产品发布、融资公告**
- 如果某条信息是 1 周前、1 个月前的旧闻，**必须先确认本周/本月是否有实质更新**，否则不收录
- 严禁把 1 个月前的爆款当"今天的新进展"凑数
- 当不确定一条信息的时效性时，必须主动搜索核实，而非凭印象判断

### 规则 2：每条信息采用统一结构
每一条目必须严格按以下结构呈现：
1. **短标题**：1 句话概括核心事实，可加 1 个标签（"重磅" / "模型发布" / "争议" / "前瞻" / "学术 × 产业" / "基础设施" 等）
2. **精简介绍**：2–5 句话，说清"是什么 / 为什么重要 / 关键数据 / 真实信号"，不要罗列细节、不要复述时间线
3. **参考链接**：分两类提供
   - **一手**：官方公告、arXiv 论文、Nature/Science 论文、GitHub Release、公司博客
   - **二手**：高质量总结性报道（机器之心、量子位、IT 之家、虎嗅、36 氪、新智元、TechCrunch、The Information、Bloomberg、AI2Work 等）
   - **参考链接数分级要求（2026-07-04 v2 — 降门槛避免丢消息）**:
     - **重磅级条目**(顶会 Oral/Spotlight、Nature/Science 论文、10 亿美元以上融资、监管重大事件):**1 个一手 + 1 个二手 = 共 2 条**
     - **一般级条目**(产品发布、合作公告、人事变动、模型迭代):**≥1 个**(优先一手,无一手时可用二手)
     - **次要级条目**(评论分析、二次解读、趋势观察):**≥1 个**(可用二手综述)
   - **每张卡 links 区域总数:4–6 条**(一手 + 二手合计)

### 规则 3：内容选择优先级（按重要性排序）
**最高优先级**：
- 重大学术突破（顶会 Oral/Spotlight、Nature/Science 论文、突破性方法）
- 重磅产品发布（OpenAI / Anthropic / Google DeepMind / Meta 等头部公司的新模型或新产品）
- 重磅融资 / 并购 / IPO 进展
- 重大政策 / 监管事件
- 头部企业重大战略调整

**次优先级**：
- 重要学术工作（顶会接收、值得关注的新方法/系统）
- 知名开源项目重大更新
- 重要人物公开发言 / 重要报告发布

**不要收录**：
- 营销性内容
- 没有新进展的旧话题
- 信息源单一、未经多源交叉验证的传闻

### 规则 5.1（2026-07-05 v6.1 新增）：sub-tags schema 与内容性质显性标注

**问题背景**：0705 简报出现"会议综述 / Claude Science 产品发布"被误判为"假学术"的情况。这类内容其实**非常前沿**，来不及作为学术成果发布，价值极高。改为**显性标注性质**，让读者一眼区分：

**标准 sub-tags schema**（每张卡片 sub-tags 区必带 1-2 个）：

| sub-tag | 含义 | 典型场景 |
|---------|------|---------|
| **「前沿产业」** | 产品发布 / 模型迭代 / 工具升级 / 商业化落地 | Claude Science 发布、Cursor iOS 推出、阿里禁用 Claude、新模型上线 |
| **「会议快讯」** | 顶会预告 / 倒计时 / 议程发布 / 颁奖消息 | ICML 2026 倒计时 3 天、WAIC 2026 开幕通知、RSS 2026 招募 |
| **「趋势观察」** | 媒体深度分析 / 行业趋势综述 / 跨事件横向比较 | "ICML 2026 透露了哪些学术硬通货"、"投稿翻倍背后 ML 换挡" |
| **「学术成果」** | 顶会 paper / Nature/Science / arXiv 论文 / 学术突破 | TUA-Bench、AdaJEPA、AI 找出 4 种新超导体（有具体 paper 引用） |
| **「产学研交叉」** | 学术侧 + 产业侧**同时有动作**（双向信号） | TUA-Bench（Stanford+Meta+Duke paper + 5 个 agent framework 集成）、Claude Code（Anthropic 引用 arXiv 隐写术 idea 落地为产品） |
| **「产品落地」** | 学术成果 → 商业产品 / 开源框架集成 | 某 paper 被集成到 vLLM / HuggingFace、ChatGPT 引用 arXiv、HuggingFace Spaces 有 demo |
| **「政策监管」** | 政策 / 出口管制 / 反垄断 / 国家安全 | Anthropic 中国禁令、美国商务部出口管制、欧盟 AI Act |

**判断标准**：
- 「前沿产业」vs「学术成果」：看核心是**产品/商业**还是**论文/方法**。**Claude Science 发布 = 前沿产业**（产品），**TUA-Bench 论文 = 学术成果**
- 「会议快讯」vs「趋势观察」：看是**纯日历消息**（"ICML 在首尔举行"）还是有**分析/观察**（"ICML 透露学术硬通货"）。前者**降级或删除**，后者保留
- 「产学研交叉」识别（满足任一即标）：
  - Paper 作者含 OpenAI/Anthropic/Google DeepMind/Meta/NVIDIA/Microsoft/Mistral/xAI/字节/阿里/腾讯/百度
  - Paper 有 GitHub release + stars >200
  - Paper 被某公司产品官方引用
  - Paper 衍生 demo 在 HuggingFace Spaces
  - 产业新闻明确提到具体 paper ID（"Anthropic 引用 arXiv:XXXX"）
  - Paper 标题含 "real-world deployment" / "production" / "in industry"

**优先级规则**：
- 标「产学研交叉」的条目优先级 +1（"观察" → "重要"，"重要" → "重磅"）

## 公众号原文采集方案（公众号原文不可直达时的兜底路径 · 2026-07-05 v6 新增）

> **本节回答的核心问题**：微信公众号原文（`mp.weixin.qq.com/s/...`）微信反爬严，webfetch 抓不到正文 / 拿到的是占位页。怎么办？
>
> **答案**：走"**公众号官网（同步站） + 搜狗微信（公开索引） + web_search（转载兜底）**"三层路径。这是当前工具组合（`web_search` + `webfetch`）下唯一可行、低成本、稳定可重复的方案。

### 三层采集路径（按优先级）

#### 🥇 第一层 · 公众号官网（首选 · 覆盖 80%）

公众号原文绝大多数会**同步到自家官网**。`webfetch` 抓官网首页 = 抓到了当天的完整文章列表。

| 公众号 | 官网 URL | 同步质量 | 推荐抓取页面 |
|---|---|---|---|
| 量子位 (QbitAI) | `https://www.qbitai.com/` | ✅ 优（全部同步） | 首页 |
| 雷峰网·AI 科技评论 (leiphone) | `https://www.leiphone.com/` | ✅ 优（带日期，全部同步） | 首页 + 业界速递列表 |
| 智东西 (zhidx) | `https://zhidx.com/` | ✅ 良（头条同步） | 首页头条 |
| 机器之心 (jiqizhixin) | `https://www.jiqizhixin.com/` | ⚠️ 中（首页是会员通讯） | **`/articles` 列表页**（不是首页） |
| 新智元 (ai-era) | `https://www.ai-era.cn/` | ⚠️ 中（常 Transport error） | 走 `web_search site:ai-era.cn` 兜底 |
| PaperWeekly | `https://www.paperweekly.org/` | ❌ 弱（依赖知乎专栏） | 走知乎专栏 + GitHub |

**抓取命令模板**：
```
webfetch("https://www.qbitai.com/")              → 提取首页近期文章标题/链接/时间
webfetch("https://www.leiphone.com/")           → 同上（带发布日期，可直接用）
webfetch("https://zhidx.com/")                  → 同上
webfetch("https://www.jiqizhixin.com/articles") → 走 /articles 页（避免会员内容挡视线）
```

**官网抓取的输出**：每篇文章拿到「标题 + 一句话摘要 + 发布时间 + 链接」就够，不需要抓正文。

#### 🥈 第二层 · 搜狗微信搜索（兜底 · 覆盖冷门号）

URL 模板（**直接 webfetch 即可**）：
```
https://weixin.sogou.com/weixin?type=2&query={关键词}&ie=utf8
```
- `type=2` = 搜文章
- `type=1` = 搜公众号
- `query` = URL 编码后的关键词

**实操示例**：
```
webfetch("https://weixin.sogou.com/weixin?type=2&query=AI%20%E5%A4%A7%E6%A8%A1%E5%9E%8B&ie=utf8")
webfetch("https://weixin.sogou.com/weixin?type=2&query=%E9%87%8F%E5%AD%90%E4%BD%8D%202026-07&ie=utf8")
webfetch("https://weixin.sogou.com/weixin?type=1&query=%E6%96%B0%E6%99%BA%E5%85%83&ie=utf8")
```

**注意**：搜狗返回的结果里，**标题 + 摘要 + 公众号名 + 时间戳都是可用的**，但 `mp.weixin.qq.com/s/...` 链接本身不可点（要微信客户端打开）。所以搜狗结果的价值是"知道这个号说了什么"，引用时要换成该号官网的同步文章 URL。

#### 🥉 第三层 · web_search 主题关键词（兜底 · 抓转载站）

如果官网 + 搜狗都抓不到（特别是新智元、PaperWeekly），用 `web_search` 命中转载站：
```
web_search("量子位 Claude Sonnet 5 site:qbitai.com")
web_search("新智元 OpenAI site:ai-era.cn")
web_search("PaperWeekly 论文 site:zhihu.com")
```

**常用转载站**（命中后 link 可信度高）：
- 知乎专栏：`zhuanlan.zhihu.com/p/xxx`
- 36 氪深度：`36kr.com/p/xxx`
- 虎嗅：`huxiu.com/article/xxx.html`
- 网易科技：`dy.163.com/article/xxx`
- IT 之家：`ithome.com/0/xxx/xxx.htm`

### 公众号原文 URL 处理规则

1. **绝对不要**把 `mp.weixin.qq.com/s/...` 当 reference 放进简报（用户无法打开，且微信占位)
2. **正确做法**：搜到公众号文章 → 找该号官网的同步文章 URL → 用官网 URL 作 reference
3. **找不到官网 URL** → 用其他媒体的同事件报道 URL 替代 → 找不到 → reference 写"无可靠链接源"
4. 例外：如果某公众号**只在公众号发、不在官网发**（极少数），则放弃收录这条

## Web Search 策略（强制执行）

### 搜索模板

每个信源至少做 **1-2 次 web_search**：

```
"{媒体名}" + "{昨日日期..今日日期}"          # 中文媒体
"{媒体名}" + "latest AI news"               # 英文媒体
"{公司名}" + "announcement" + "{今日日期}"    # 公司动态
"{公司名}" + "release notes" + "{今日日期}"   # 产品发布
```

**实际查询示例**：
- `量子位 2026-07-03`
- `QbitAI latest AI news`
- `OpenAI announcement July 2026`
- `月之暗面 Kimi 7月3日`
- `智谱 GLM 2026-07-03`
- `Anthropic news July 2026`

### 筛选规则（避免收录旧闻）

每个搜索结果必须：
- ✅ **检查发布日期**：必须是 24-48 小时内
- ✅ **提取元信息**：标题、摘要、发布时间、URL
- ✅ **验证新鲜度**：对超过 48 小时但标记为"重要"的，主动搜 `"{关键词} July 2026 update"` 找后续进展
- ❌ **不要收录**：1 周前的旧闻、无新进展的话题、营销性内容、单一信源未经印证

### 抓取流程（每个信源）

1. web_search 1-2 次，拿到 5-10 个候选 URL
2. 对最相关的 1-2 个 URL 调 web_fetch 拿全文（如果时间允许）
3. 提取关键信息：标题 + 100-200 字要点 + URL
4. 标记信源可信度（一手 / 二手 / 行业洞察）
5. 分类到对应主题块（按"规则 5"的主题分块）

### 效率要求

- 6+ 个信源的 web_search **必须并行**（用 multi-tool 并行）
- 总信源搜索时间控制在 3-5 分钟内
- 不需要每个信源都 fetch 全文，只在标题有意思时 fetch

### 信源平衡

每个主题块下，**至少 2 个不同信源**（避免单一来源偏见）：
- 国内动态：1 国内 + 1 海外（如有海外报道）
- 海外动态：1 一手（公司官方）+ 1 二手（媒体）
- 学术动态：1 arXiv/paper + 1 中文媒体解读（如有）

### 输出格式

每条信源条目在卡片里需标注：
```
来源：[媒体名] · [一手/二手] · [发布时间]
```

例：
- 来源：OpenAI 官方博客 · 一手 · 2026-07-03
- 来源：量子位 · 二手 · 2026-07-03

## 链接质量与验证规则（强制执行 — 用户要求）

reference 链接是简报可信度的核心。**错的链接比没有链接更糟糕**。

### 用户反馈的常见错误（必须避免）

❌ **错误 1：企鹅号/微信封闭生态链接**
- 例：`https://企鹅号/#tencent-dfae9b96-96dd-4c1a-b5fe-32f5c8ead41b-10`
- 原因：腾讯封闭生态，公网/搜索引擎抓不到，用户点不开
- 规则：**完全不收录这类信息**（宁可放弃这条，也不给死链）

❌ **错误 2：官方网站首页**
- 例：给"月之暗面 315 亿美元融资"时，reference 给 `https://www.moonshot.cn/`
- 原因：首页不指向具体内容，读者点开找不到这条新闻
- 规则：**必须是官网提供的具体文章页 / 公告页 URL**，找不到就标记"无可靠官方链接"

### news.qq.com 等反爬占位的「假成功」检测（**v6 新增 — 用户 7-3 发现 2 例**）

**问题（用户在 https://daily-ai-2o3.pages.dev/ai-daily/2026-07-03/#c-2-1 实测发现）**：

`https://news.qq.com/rain/a/20260701A03CIY00` 和 `https://news.qq.com/rain/a/20260630A079ST00` 用浏览器 UA 测试：
- HTTP 状态码 = 200 ✓（curl `-w "%{http_code}"` 看起来成功）
- **但实际抓取到的 body 是「宝贝回家」公益页 `https://h5.news.qq.com/static/babyhome.htm`**，不是新闻文章
- 即：**该 URL 的原始文章已被腾讯删除，但 URL 没释放（搜索引擎还能搜到）**

**用户反馈原话**："虽然可以链接成功 你http测试是200，但是里面的内容是404page内容，这是假成功。"

**识别规则 — Step 0：HTTP 200 后必须 verify content**

```
⚠️ HTTP 200 ≠ URL 真的可用
⚠️ 必须验证最终 URL（curl -L follow redirects）和 body 内容

检测脚本：
  result=$(curl -sS -A "Mozilla/5.0 ... Chrome/120" -L -o /tmp/_body --max-time 10 \
           -w "%{http_code}|%{url_effective}" "URL")
  code=$(echo "$result" | cut -d'|' -f1)
  final_url=$(echo "$result" | cut -d'|' -f2)

  # 三个假成功信号（任一命中 → URL 是 fake success）：
  1. final_url 不等于原 URL（被 302 重定向）— 尤其是重定向到以下域名：
     - h5.news.qq.com/static/babyhome.htm    ← 腾讯文章被删的统一占位
     - *.qq.com/404.htm / *.qq.com/error.htm
     - 任何 `/babyhome|notfound|deleted|canceled` 关键字路径
     - 任何 social/welcome/splash/landing 占位页
  2. body 包含 "页面不存在" / "文章已删除" / "找不到该网页" /
     "很抱歉，您访问的页面不存在" / "该内容已被删除" / "腾讯宝贝回家" / "404 Not Found"
  3. body 大小 < 2KB（反爬占位极短，正经文章至少 10KB+）

  三者任一命中 → 标记 [FAKE-200] → 找替代源
```

**特别注意 — 已知 fake-success 模式库**（持续累积）：

| URL 模式 | 真状态 | 原因 |
|---------|-------|------|
| `news.qq.com/rain/a/2026MMDDA[数字]00` 形式但 302→babyhome | ❌ 已删除 | 腾讯文章下架后保留 URL 给搜索引擎 |
| `企鹅号/#tencent-xxxx-yyy-n` | ❌ 永远死链 | 封闭生态，curl 也抓不到 |
| `*.sina.cn/article_xxxx` 形式但返 200 + 反爬 banner | ❌ 假成功 | 新浪部分聚合页对 UA 严格 |
| `mp.weixin.qq.com/s/...` 但需验证码 | ❌ 假成功 | 必须微信客户端打开 |

**操作流程**（强制执行）：

1. 每个 URL 用 `-L` follow redirects 后看 `url_effective` 字段
2. 如果 `url_effective` 包含 `babyhome|404|notfound|deleted` → 立即判 [FAKE-200]
3. 即使 url_effective 跟原 URL 一致，也要 grep body 里的 "页面不存在" / "已删除"
4. body 大小 < 2KB → 立即判 [FAKE-200]
5. 验证不通过 → 重新搜替代源（按密度补救方法论 Step 1-7）
6. 验证通过 → 才放入 ref 列表

**反例对照（实测 7-3 失效链接）**：

| URL | curl -L 结果 | 判定 |
|-----|------|------|
| `news.qq.com/rain/a/20260701A03CIY00` | 302→`h5.news.qq.com/static/babyhome.htm?pgv_ref=apub` | ❌ [FAKE-200] 文章已删 |
| `news.qq.com/rain/a/20260630A079ST00` | 302→同上 | ❌ [FAKE-200] 文章已删 |
| `news.qq.com/rain/a/20260630A08EB500` | 200 OK + final_url 不变 + 真实文章 body | ✅ 真成功 |
| `news.qq.com/rain/a/20260630A05LBF00` | 200 OK + final_url 不变 + 真实文章 body | ✅ 真成功 |
| `stcn.com/article/detail/3989598.html` | 200 OK + 真实文章 | ✅ 真成功 |
| `m.jiemian.com/article/14671289.html` | 200 OK + 真实文章 | ✅ 真成功 |

→ cron 在 Step 6 链接验证里加入 `curl -L` follow + babyhome 检查，否则会把被删文章当作成功链接留给用户。

### 链接密度保障（强制执行 — 每张卡片 ≥2 个 ref）

**这是用户 2026-07-03 最强烈的反馈："0 真问题链接 ≠ 0 问题；密度也要保证"。**

> 宁可少收录 1-2 个事件，也比事件密集但 ref 密度低更好。
> 你都花了时间搜到这个事件，再花 30 秒搜它的第二个 ref —— 这个时间投入完全值得。

**硬性规则**：
- ✅ **每张 card 至少 1 个有效 ref**（**1 个是必需的；≥2 是推荐但不强制**）
- ❌ **绝不允许出现空 `<ul></ul>` 容器**（必须填满 1 个 ref 或删除整张卡片）
- ❌ **不允许出现"为了凑数 ≥2 而用错配 URL"的情况**（2026-07-03 用户实测发现:把 Kimi 卡片用 Kimi 文章 + 智谱文章凑成 2 条 ref，但其中一条 URL 跟卡片事件不匹配——这比 1 条 ref 更糟糕）
- ❌ **绝不允许 `<ul>` 里出现 2 个完全相同的 URL**（搜索引擎有时会返回多个相同链接，只算 1 个独立源）
- ❌ **绝不允许把 URL 从一个事件"借用"到另一个事件凑数**

**违反密度规则的常见 cron 输出症状**（用户称"密度问题"）：
- `<ul>` 是空的（cron 把所有链接都判定为"未验证"就删了 ul 但忘了清空容器）
- `<ul>` 里 2-3 条但所有 URL 都指向同一域名（如全给 news.qq.com）—— 形式上看有，但实质上没"多源验证"
- `<ul>` 里 2 条但其中一条 URL 跟卡片事件不匹配（错配问题，比密度低更严重）

**正确的密度策略**：
- 搜到 1 个具体的、真实的 ref → 用 1 个（**这是合格状态**）
- 搜到 2 个具体 ref → 用 2 个（**锦上添花**）
- 只搜到首页 / 占位符 / 错配的 URL → 宁可 1 个 ref 也不要凑数错配
- 完全搜不到 → 删除卡片,事件要点合并到"编辑小结"

**密度补救流程**（可选 — 锦上添花,不强制凑数）：
1. 如果**搜到 1 个真实的、具体的、与事件匹配的 ref** → 直接用,不需要凑 ≥2
2. 如果想加第二个 ref → 用原关键词再搜一次，加 `site:{不同媒体域名}` 或换媒体名（财联社 → IT之家 → 36氪 → 雪球）
3. 搜 arXiv 论文（如有学术事件）
4. 搜外媒：英文关键词 + Reuters/Bloomberg/FT/The Verge
5. **千万不要为了凑 ≥2 而用错配的 URL**（把别的事件的 URL 放进来凑数）
6. 实在搜不到第二个 ref → 维持 1 个 ref 即可,**完全合格**
7. 不要连续 3 次搜同一关键词没结果就放弃 —— 换关键词试试（如"月之暗面 315 亿"可以换成"Moonshot 315"或"中国 AI 公司 融资 估值 7月"）

### 链接类型优先级（从高到低）

1. **具体文章页 / 博客 post**（e.g., `https://blog.openai.com/2026-07-03-gpt5`）
2. **公司新闻页 / Press Release**（e.g., `https://www.moonshot.cn/news/2026/07/03/kimi-update`）
3. **arXiv 论文页**（e.g., `https://arxiv.org/abs/2507.01234`）
4. **Product Hunt 产品页**（e.g., `https://www.producthunt.com/posts/xxx`）
5. **GitHub Release / Issue / PR**（e.g., `https://github.com/owner/repo/releases/tag/v1.0`）
6. **特定推文 / X 状态**（e.g., `https://x.com/user/status/1234567890`）
7. **媒体具体报道页**（e.g., `https://www.qbitai.com/2026/07/03/12345.html`）

### 严格禁止的链接类型

- ❌ **官网首页 / 域名根**（`https://www.moonshot.cn/`、`https://openai.com/`、`https://www.qbitai.com/`、`https://www.zhiding.cn/`、`https://deepseek.ai/`、`https://www.deepseek.com/`、`https://news.qq.com/`）— 不指向具体内容
- ❌ **企鹅号内部链接**（`https://企鹅号/#tencent-xxx`）— 封闭生态
- ❌ **微信公众号发布用户 hash 链接**（`https://企鹅号/#tencent-xxx-yyy` 或 `https://mp.weixin.qq.com/mp/homepage?...&__biz=xxx` 这类指向"用户主页"或"公众号页面"的链接）— 用户看不到具体文章
- ❌ **微信公众号文章链接必须是 `https://mp.weixin.qq.com/s/...` 格式** — 这个 `s/` 后面的 hash 才是具体文章的 ID,点开是文章详情页
- ❌ **404 / 死链**（即使搜索引擎返回了）
- ❌ **社媒主页**（`https://twitter.com/karpathy`、`https://x.com/ylecun`）— 不指向具体内容
- ❌ **不带具体路径的根域名**
- ❌ **带 tracking 参数的链接**（如 `?utm_source=...&fbclid=...`）— 用干净 URL
- ❌ **"via" / "据报道"占位文本**（不是 URL 的占位文本）
- ❌ **任何 HTTP（非 HTTPS）链接**

### 链接验证流程（强制执行 — 每条 reference 必做,**HTTP 200 ≠ URL 真可用**）

**Step A：URL 形式检查**
```
✓ 必须是 https:// 开头
✓ 必须有具体路径（至少 1 段，如 /news/2026/...）
✓ 域名必须是真实顶级域名（不是占位符或内部哈希）
✓ 不能是 # 锚点链接（公众号 hash 跳转形式）
✓ **关键：URL 不能以域名结尾（即不能是 https://www.xxx.com/ 这种首页形态）**
  → 至少要有 1 段路径（/articles/.../、/news/.../、/detail/...html 等）
  → 不允许 https://www.qbitai.com/、https://www.tmtpost.com/ 这种纯首页
```

**Step B：HTTP HEAD 验证**（用 curl — 仅作初步参考）
```bash
curl -sI -o /dev/null -w "%{http_code}\n" --max-time 15 "https://..."
# 200/301/302 算初步通过 ✓ (但不代表 URL 真可用,见 Step B.5)
# 404/403/500/timeout 算失败 ✗
```

**Step B.5（关键 — 2026-07-03 用户反馈：HTTP 200 ≠ URL 真可用）**：
很多网站会做 anti-bot,返回 HTTP 200 但 body 是占位页/404/反爬挑战。**必须**做下面检查:
```bash
# 用真实 UA 抓取,follow redirects
body=$(curl -sSL -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/120.0" \
        --max-time 15 -L "https://...")
final_url=$(curl -sSI -A "Mozilla/5.0..." --max-time 10 -L -o /dev/null -w "%{url_effective}" "https://...")
```

**假成功信号（任一命中 → URL 是 fake-success）**：
1. `final_url` 不等于原 URL（被 302 重定向）到以下域名:
   - `h5.news.qq.com/static/babyhome.htm` ← 腾讯文章被删的统一占位
   - `*.qq.com/404.htm` 或 `*.qq.com/error.htm`
   - 任何含 `/babyhome`、`/notfound`、`/deleted`、`/canceled` 的路径
   - 任何 social/welcome/splash/landing 占位页
2. body 包含 "页面不存在" / "文章已删除" / "找不到该网页" / "很抱歉,您访问的页面不存在" / "该内容已被删除" / "404 Not Found"
3. body 大小 < 2KB（反爬占位极短,正经文章至少 10KB+）

**任一命中 → 标记 [FAKE-200] → 走 Step D fallback**

**Step C：内容相关性检查**
- 用真实 UA + follow redirects 抓取页面 HTML
- 提取 `<title>` 和前 500 字符正文
- **标题必须包含事件关键词**（如"Grok 4 发布"必须出现在 title 中）
- 标题含 "404" / "Page Not Found" / "Access Denied" / "页面不存在" → 标记死链
- 标题与事件不匹配 → 标记假阳性（搜索结果与事件无关）→ 删除该 li

**Step D：替代源重搜 / Fallback（[FAKE-200] 或死链时强制执行）**
- **不要**试图 hack 同一个 URL（换 UA、换 referer 等通常没用）
- 直接搜替代源:
  1. `"{事件关键词}" "{原媒体名}"` — 找原媒体家的另一篇报道
  2. `"{事件关键词}" site:{原域名}` — 站内搜索
  3. `"{事件关键词}" site:reuters.com` / `site:bloomberg.com` / `site:ft.com` — 外媒
  4. `"{事件关键词}" site:tmtpost.com` / `site:qbitai.com` / `site:jiqizhixin.com` — AI 媒体
  5. 实在搜不到 → **删除该 ref**(允许 1 个 ref 状态)
  6. 全部搜不到 → **删除整张卡片**,事件要点合并到"编辑小结"

### 死链/不可访问链接处理原则

1. **优先降级**：一手链接失效时，找二手媒体的具体文章页替代
2. **可降级的二手**：量子位 / 机器之心 等的具体报道页
3. **不收录**：找不到任何可访问具体文章页时
4. **宁可少收条目，也不要给错链接**：用户对错链接 0 容忍

### 密度补救方法论（2026-07-03 实战总结）

当某张卡片 web_search 第一轮只返回首页 / 聚合页（企鹅号 / 腾讯网聚合），按以下顺序救活：

**Step 1：换关键词 + 加 site 限定符**
```
例：搜"月之暗面 315 亿 估值" 第一轮返回的全都是聚合页
第二轮：
  "月之暗面" "315亿美元" site:ithome.com
  "月之暗面" site:donews.com
  "Kimi" "315亿" site:stcn.com
```

**Step 2：换英文 / 拉丁化公司名**
```
例：搜"月之暗面" → 换 "Moonshot AI 315 亿"
搜"葡萄牙 AMALIA 大模型" → 换 "AMALIA Portugal LLM open source"
```

**Step 3：换时间维度**
```
当前事件是 7-2 发生 → 搜 "7月2日" + 事件 + 媒体
但 7-1 准备期可能也有该事件报道 → 搜 "7月1日" + 事件 + 媒体
```

**Step 4：跨语种 / 跨地域**
```
同一事件在 Reuters / Bloomberg / FT 可能有英文版 → 看英文报道
同一事件在中文可能在网易 / 新浪 / 腾讯文章页 → 看具体子站
新闻聚合类（如凤凰网科技 ifeng.com/c/...、网易新闻 163.com/dy/article/...）通常回率最高
```

**Step 5：搜"权威公司+事件"**
```
事件涉及具体公司时，搜 "{公司名} {事件}" 通常能命中公司新闻稿
例：月之暗面 → 搜 "Moonshot Kimi funding round"
例：智谱 → 搜 "智谱 GLM-5.2 发布"
```

**Step 6：腾讯新闻文章 URL 是真实可用的**
格式：`https://news.qq.com/rain/a/YYYYMMDDAAxxxxxx` 是稳定的 article URL
但是用 `curl` 默认 UA 会返 501（反爬），用户浏览器正常 200
- **判断逻辑**：搜到腾讯新闻文章 URL 后，可信度判定为 ✓（已知 UA 问题，浏览器正常）
- **不要因此判它为不可访问 URL 而删掉**

**Step 7：兜底策略 = 接受 2 个二手 URL**
- 一手 + 二手已经合格（每条 reference 必须"具体文章页"，二手达标）
- 如果一手死活搜不到，2 个二手 + 1 个 arXiv 也是 OK 的
- 不要给 twitter.com/facebook.com 等社媒主页占位
- 不要给 `${公司域名}.com/` 这种首页占位

### 输出格式（每条 reference 必须带验证状态）

```
一手：[具体文章URL] ✓ (HTTP 200, 标题匹配)
二手：[具体文章URL] ✓ (HTTP 200, 标题匹配)
```

如果某条目找不到**任何可验证的具体文章页链接**：
- **保留事件描述**（事件本身是新闻）
- **reference 区写 "无可靠链接源"**
- **不要给假链接凑数**（首页/占位符/不可访问链接）

### 反例对照

| 信息 | ❌ 错 | ✅ 对 |
|------|-------|-------|
| 月之暗面 315 亿融资 | `https://www.moonshot.cn/` | `https://www.moonshot.cn/news/...`（具体公告页）<br/>或 `https://www.qbitai.com/2026/07/02/xxx.html`（媒体具体报道）<br/>或直接标"无可靠官方链接" |
| Karpathy 推文观点 | `https://twitter.com/karpathy` | `https://x.com/karpathy/status/1234567890`（具体推文） |
| OpenClaw 移动端上架 | `https://企鹅号/#tencent-xxx` | 直接不收录（信息源不可访问）<br/>或换有具体链接的二手报道 |

## 工作流（生成前必走的步骤）

### Step 1：并行搜索（**严格按上方"信源清单"section 覆盖**）
**必须**对信源清单中每个信源做 1-2 次 web_search（中文媒体搜 "[媒体名] [今日日期]" 模板，英文媒体搜 "[媒体名] latest AI news"），从结果里筛选 24-48 小时内真实发布的内容。**这是搜索的全部起点**，不要凭印象列信源。

按以下类别并行覆盖（具体名单见信源清单）：
1. arXiv / 顶会最新论文（按当前时间段搜 ICML/NeurIPS/ACL 等）
2. 海外头部公司官方（OpenAI / Anthropic / DeepMind / Meta AI / NVIDIA / Mistral / xAI / Apple ML / Cohere / Stability）
3. 国内大模型公司官方（智谱 / Kimi / 字节豆包 / 阿里通义 / 百度文心 / 腾讯混元 / 华为 / 阶跃 / Minimax / DeepSeek / 面壁）
4. 国内一线 AI 媒体（量子位 / 机器之心 / 新智元 / AI 科技评论 / 智东西 / 36 氪 / 雷峰网 / 硬地骇客 / 夕小瑶 / PaperWeekly / 赛博禅心）
5. 全球英文媒体（The Information / TechCrunch AI / The Verge AI / MIT Tech Review / VentureBeat / The Decoder / Import AI / Last Week in AI / Hugging Face Blog）
6. 资本/融资/监管/具身智能 等专题（按"信源清单"对应方向搜）

并行执行不要串行。每个信源 1-2 次 web_search 足够，覆盖率优先。

### Step 2：信息核实（关键步骤，不可跳过）
- 对每条候选信息，搜索其发布日期，确认是"今天/本周"的新进展
- 如果是 1 周前后的旧新闻，必须搜索"[关键词] July 2026" 看是否有后续更新
- 对 AI 智能体、科研 Agent 这种热点话题，主动搜索"2026-07"看是否有今天的新动作

### Step 3：分类与排序
- 按"规则 3"的优先级排序
- 分配到对应主题块
- 给每条选一个合适的标签 + 2-3 个 sub-tags

### Step 4：撰写并成稿
- 严格按"规则 2"的统一结构写
- 每条 2–5 句精简介绍，避免冗长
- 链接必须有 1 个一手 + 1 个二手

### Step 4.5：内容质量自检 SOP（2026-07-05 新增 — 解决"重复 + 旧闻 + 假 URL"三大问题）

> **背景**：0705 简报出现 60-70% 内容重复、学术不精确、URL 全是"假设的"三大问题。本节强制三道闸门，**全部通过才能进 Step 5**。

#### 4.5.1：24-48h 新鲜度强制过滤

**所有 candidates 的 date 字段必须 >= 今天-1**。超过 48 小时的候选一律剔除。

```
判定规则：
- date = 今天 → 保留
- date = 昨天 → 保留
- date >= 前天 → 标记 [STALE]，从列表删除
- date 未知 → 必须主动 web_search "{标题} {今日日期}" 验证时效，仍未知则 [STALE]
```

**常见 [STALE] 反例（0705 简报踩过的坑）**：
- ❌ 1 周前的融资公告（除非本周有实质更新）
- ❌ 1 个月前的产品发布（如智谱 GLM-5.2 6-13 发布的，不能当 7-5 的新进展）
- ❌ 上一届顶会（已闭幕的 NeurIPS 2025 不能算 2026 进展）
- ❌ 已过期的 deadline 倒计时

#### 4.5.2：URL 真实 fetch 验证（反"假设 URL"）

**对每个候选的"一手 URL"和"二手 URL"做 webfetch，禁止任何"假设的"或"待补"的占位 URL 进入 candidates 列表**。

```
fetch 失败的标记规则：
1. HTTP 200 + body > 2KB + title 包含事件关键词 → [OK]
2. HTTP 200 + body < 2KB → [DEAD]（反爬占位 / babyhome 类）
3. HTTP 200 + body 含 "页面不存在" / "文章已删除" / "404" → [FAKE-200]
4. HTTP 200 + final_url 跳转到 babyhome.htm / 404.htm / deleted → [FAKE-200]
5. HTTP 4xx / 5xx / timeout → [DEAD]
6. URL 是首页（以 .com/ 或 .cn/ 结尾，无具体路径）→ [DEAD]（违规，规则 2）
7. URL 是企鹅号 / 微信 hash 链接 → [DEAD]（封闭生态）
8. 没有 URL → [NO-REF]
```

**[DEAD] / [FAKE-200] / [NO-REF] 的候选必须重新 web_search 替代 URL，仍失败则标记 `[NO-REF]` 但写 "无可靠链接源"，Step 5 生成时跳过**。

**0705 简报踩过的坑**（必须避免再犯）：
- ❌ "https://openai.com/blog/gpt-5-6 (**假设官方**)" — 直接判 [NO-REF]
- ❌ "https://www.zhipuai.cn/ (**智谱官方**)" — 首页,直接判 [DEAD]
- ❌ "https://www.qbitai.com/2026/07/05/..." — URL 没填完整,直接判 [NO-REF]
- ❌ "https://www.qbitai.com/ (量子位首页头条)" — 首页,直接判 [DEAD]

#### 4.5.3：7 天去重（反"重复事件"）

**自动去重：从过去 7 天 `repo/ai-daily/2026-07-*/index.html` 抽取所有 card title，与当前 candidates 比对**。

```
去重算法：
1. 读 repo/ai-daily/2026-07-{今天-1,今天-2,...,今天-7}/index.html 全部
2. 用 regex 抽取 <h3 class="card-title">...</h3> 或 <div class="card-title">...</div>
3. 关键词匹配：候选标题与历史标题有 ≥3 个共同关键词（>3 字符） → 标记 [DEDUPLICATED]
4. 例外：同一事件的"后续进展"（如 7-4 阿里禁用 Claude → 7-5 Qoder 接棒）不去重
```

**[DEDUPLICATED] 的候选从 candidates 列表删除**。

**0705 简报踩过的坑**（必须避免再犯）：
- ❌ Claude Science 发布（0701 已收录过）
- ❌ 阿里禁用 Claude Code（0704 已收录过）
- ❌ Claude Sonnet 5 差评（0703 已收录过）
- ❌ 月之暗面 315 亿融资（0702 / 0704 已收录过）
- ❌ Fable 5 全球解禁（0701 / 0703 / 0704 已收录过）
- ❌ DeepSeek V4 峰谷定价（0630 / 0704 已收录过）

**只有真正"24h 内新发生的事件"才能进 24 张卡**。如果 7 天内的事件太多，应该减少"重复的子领域"而增加"新出现的子领域"。

#### 4.5.4：事件指纹去重（2026-07-05 v6.2 升级 — 替代标题关键词匹配）

**问题**：4.5.3 标题关键词匹配**失效**。cron 跑 0705 时,0701 的"Claude Science 发布"被 0705 的"Claude Science 助力科研自动化"(同事件不同标题)漏掉,导致 38% 重复率。

**升级方案**:**事件指纹** = `公司 | 事件类型 | 日期`,而非简单标题关键词。

```
事件指纹生成：
1. company = extract_company(title)  # Anthropic / 月之暗面 / 阿里 / 字节 / OpenAI / DeepSeek / 智谱 / Google / Meta / 华为 / ...
2. event_type = extract_event_type(title)  # 产品发布 / 模型迭代 / 融资估值 / 禁令政策 / 评测基准 / 收购合作 / 学术成果 / ...
3. fingerprint = f"{company}|{event_type}"

例:
- "Anthropic Claude Science 科研工作台" → fingerprint = "Anthropic|产品发布"
- "Claude Science 助力科研自动化" → fingerprint = "Anthropic|产品发布" → 同事件 → [DEDUPLICATED]
- "阿里达摩院 ElementsClaw 智能体发现 4 种超导体" → fingerprint = "阿里|学术成果"
- "月之暗面 315 亿融资" → fingerprint = "月之暗面|融资估值"
- "月之暗面 K3 发布" → fingerprint = "月之暗面|产品发布" → 不同事件类型 → 保留
```

**判定规则**:
- 同一 fingerprint 在历史 7 天**出现过 1 次**:新候选视为"同事件后续" → 标记 [DEDUPLICATED] → **删除**
- **例外**(允许保留):"产品发布" → "产品迭代" / "融资估值" → "估值变化" / "禁令" → "解禁" 视为**不同事件**,保留

#### 4.5.5：同一公司同类事件 7 天频率限制（2026-07-05 v6.2 新增）

**问题**：0705 简报里 Anthropic / 月之暗面 / 阿里 各占 3-4 条,过度挤占其他公司。

**限制规则**(每期 cron 强制):

| 事件类型 | 7 天内同公司上限 |
|---------|--------------|
| 融资估值 | 1 条主线 + 1 条后续 |
| 产品发布 | 2 条(同一产品线合并) |
| 禁令 / 政策 | 1 条 |
| 学术成果 | 不限(鼓励多公司 paper) |

**超出限制的处理**:
- 不直接删除,**降级到主题 6 (前瞻)**,作为"未来关注"提及
- 例:0705 简报里月之暗面 3 条(融资 / K3 / 张潼演讲) → 保留融资主线 + K3 合并,张潼演讲降级到前瞻

#### 4.5.6：cron Step 2 采集阶段强制规则（2026-07-05 v6.2 新增）

**5 个强制参数**(在 cron prompt 加):

1. **所有 web_search 必须用 `freshness="day"`** — 强制 24h 内结果
2. **所有 query 必须含今日日期关键词**:
   - 中文：`"2026年7月5日"` / `"今日"` / `"今天"`
   - 英文：`"July 5 2026"` / `"today"`
   - 例：`web_search("Anthropic Claude 2026-07-05", freshness="day")`
3. **多源印证 24h 占比 ≥70%**:candidates 写完后,统计 `candidates_with_24h + candidates_with_48h * 0.7` 占比,< 70% 触发重采
4. **每条候选必须有发布日期**:`date` 字段必填(没有日期的候选直接 [STALE])
5. **避免二手转载**:媒体 A 转媒体 B 的"7-3 旧闻"在 7-5 被搜到 → 优先找 7-5 当天的原始信源,否则标 [STALE-转载]

**重采触发 SOP**:
```
if fresh_ratio < 0.7:
    print("⚠️ 24h 占比过低({:.0%}),触发重采")
    re_collect_keywords = [
        f"{公司名} 2026年7月5日",
        f"{事件关键词} 今天",
        f"{公司名} July 5 2026"
    ]
    对每条重采关键词跑一次 web_search,freshness="day"
    合并结果到 candidates
    重新跑 4.5.1-4.5.5
```

## 反例（避免犯的错误）

❌ **错误 1**：把一个月前的爆款当今天的新闻
> 例：把 1 月发布、3 月爆火的 OpenClaw 当作 7/2 的"实时动态"塞进简报
✅ **正确做法**：搜索"OpenClaw 2026 年 7 月"找到 6/30 移动端上架这种真实近期进展

❌ **错误 2**：把"学术"和"具身智能"对立分块
> 例：把"学术"和"具身智能"对立分块
> 例：把"具身智能"作为一个大主题单独列出，导致其他 AI 方向（如 AI for Science、Agent）看上去与具身对立
✅ **正确做法**：用"通用智能与机器人"这种大主题名，把具身、VLA、世界模型、Agent 网关作为子领域

❌ **错误 3**：条目只写产业意义，不写学术贡献；或反之
✅ **正确做法**：用 🎓 学术 / 🏢 产业 双视角框，对每条都明确写出两个层面的意义

❌ **错误 4**：每条介绍写得很长，像产品评测
✅ **正确做法**：2–5 句话精简介绍，重点说"是什么 / 为什么重要 / 关键数据 / 真实信号"

❌ **错误 5**：链接全是二手转载，没有一手源
✅ **正确做法**：每条至少 1 个一手（官方公告/论文/博客）+ 1 个二手（高质量媒体）

❌ **错误 6**：信息源单一、不去交叉验证
✅ **正确做法**：重要信息（如融资、产品发布）至少 2 个独立来源印证

- **computer use（cu MCP）**：cron session 默认**不可用**（无 GUI），不要尝试

## 失败恢复机制（STATE 文件 · 2026-07-05 新增）

cron 跑失败时**不重试**（避免同一天多次 commit），但支持**断点续跑**：通过 STATE 文件记录进度，下次 cron 启动时自动识别已完成步骤。

### STATE 文件位置

```
D:\ECNU\其他\每日AI推送\.cron-state.json
```

### STATE 文件 schema

```json
{
  "date": "2026-07-05",
  "started_at": "2026-07-05T09:00:30+08:00",
  "last_updated": "2026-07-05T09:25:15+08:00",
  "candidates_generated": true,
  "candidates_path": "D:\\ECNU\\其他\\每日AI推送\\2026-07-05\\candidates-2026-07-05.md",
  "freshness_filtered": true,
  "url_verified": true,
  "deduplicated": true,
  "html_generated": true,
  "html_path": "D:\\ECNU\\其他\\每日AI推送\\2026-07-05\\index.html",
  "git_committed": true,
  "git_pushed": false,
  "deploy_verified": false,
  "error_log": []
}
```

### 续跑 SOP（cron 启动时第一步执行）

```
1. 读取 .cron-state.json
2. 如果不存在 → 全流程跑
3. 如果存在且 date == 今天 → 跳过已完成步骤:
   - candidates_generated=true → 跳过 Step 2 采集阶段
   - freshness_filtered=true → 跳过 Step 2.5 新鲜度过滤
   - url_verified=true → 跳过 Step 2.6 URL 真实验证
   - deduplicated=true → 跳过 Step 2.7 7 天去重
   - html_generated=true → 跳过 Step 3 生成阶段,直接到 Step 4 部署
   - git_pushed=true → 跳过 git push
   - deploy_verified=true → 全跑完,删除 STATE,报告成功
4. 如果存在但 date != 今天 → 删除旧 STATE,启动新一轮
5. 在每个步骤完成后立即原子更新 STATE 对应字段(写 .tmp 然后 rename)
```

### 完整 Step 列表（更新 STATE 用）

```
Step 1: 准备工作 → 立刻创建 STATE
Step 2: 采集 → 完成后 candidates_generated=true
Step 2.5: 24-48h 新鲜度过滤 → freshness_filtered=true（详见 `### Step 4.5：内容质量自检 SOP - 4.5.1`）
Step 2.6: URL 真实 fetch 验证 → url_verified=true（详见 `### Step 4.5 - 4.5.2`）
Step 2.7: 7 天去重 → deduplicated=true（详见 `### Step 4.5 - 4.5.3`）
Step 3: 生成 HTML → html_generated=true
Step 4: 部署（git push + Cloudflare 验证）→ git_pushed=true + deploy_verified=true
Step 5: 收尾（删 STATE + 报告）
```

### STATE 文件生命周期

- **创建**：cron session 启动时立即创建（即使后面失败也有记录）
- **更新**：每个 step 完成时更新
- **删除**：deploy_verified=true 后删除（表示完全成功）
- **保留**：cron session 失败/挂起时保留，下次 cron 自动识别

**每日自动部署流程**（生成 HTML 后必须执行）：

```powershell

$workspace = "D:\ECNU\其他\每日AI推送"
$repoRoot = "$workspace\repo"
$portalTpl = "$workspace\portal-template.html"

if (Test-Path $dailyHtml) {

    Write-Host "✓ Daily brief → ai-daily/$date/index.html"
} else {
    Write-Host "✗ Daily brief not found at $dailyHtml"
    exit 1
}

# ============ Step 2: Portal → repo/index.html (首页 — 只更新"今日"日期戳 + Card 1 链接 + 往期数量 + 删除 cdn 链接) ============
$portalContent = Get-Content $portalTpl -Encoding UTF8 -Raw
# 替换 3 处日期占位符(必须一次性替换,因为 deploy 脚本会一次执行):
#   - Card 1 href: "./ai-daily/YYYY-MM-DD/"
#   - Card 1 card-link: "/ai-daily/YYYY-MM-DD/"
#   - Card 1 card-tag: "今日已推送 · YYYY-MM-DD"
$portalContent = $portalContent -replace "今日已推送 · \d{4}-\d{2}-\d{2}", "今日已推送 · $date"
$portalContent = $portalContent -replace '\./ai-daily/\d{4}-\d{2}-\d{2}/', "./ai-daily/$date/"
$portalContent = $portalContent -replace '/ai-daily/\d{4}-\d{2}-\d{2}/', "/ai-daily/$date/"

# 2026-07-04 v2: 自动化更新"往期 N 期已收录"
# 扫描 ai-daily/ 目录,统计 YYYY-MM-DD 子文件夹
$archivedCount = (Get-ChildItem -Path "$repoRoot\ai-daily" -Directory -ErrorAction SilentlyContinue | Where-Object { $_.Name -match '^\d{4}-\d{2}-\d{2}$' }).Count
$portalContent = $portalContent -replace '(\d+)\s*期已收录', "$archivedCount 期已收录"
Write-Host "✓ Portal 往期已收录数: $archivedCount"

# 2026-07-04 v2: 删除 cdn.jsdelivr.net 链接(用户硬性要求不暴露)
$portalContent = $portalContent -replace '(?s)<a href="https://cdn\.jsdelivr\.net[^"]*"[^>]*>.*?</a>', ''
$portalContent = $portalContent -replace 'cdn\.jsdelivr\.net', ''

# 2026-07-04 v4: portal 黑名单 — 删除 raw.githubusercontent.com 链接(用户硬性要求)
$portalContent = $portalContent -replace '(?s)<a href="https://raw\.githubusercontent\.com[^"]*"[^>]*>.*?</a>', ''
$portalContent = $portalContent -replace 'raw\.githubusercontent\.com', ''

# 2026-07-04 v4: 删除 /example/ 链接(公网 404)
$portalContent = $portalContent -replace '(?s)<a href="[^"]*/example/[^"]*"[^>]*>.*?</a>', ''

# 2026-07-04 v4: 替换 brand-row 错误文案
$portalContent = $portalContent -replace 'CDN 加速', '每日推送 · 全球视野'
Write-Host "✓ Portal 已清理黑名单 URL + brand-row 文案"

Set-Content "$repoRoot\index.html" -Value $portalContent -Encoding UTF8 -NoNewline
Write-Host "✓ Portal → index.html (今日已推送 · $date, Card 1 → ./ai-daily/$date/, 往期 $archivedCount 期)"

# ============ Step 3: archive.html (可选,如果 cron 生成了新版) ============
if (Test-Path "$workspace\archive.html") {
    Copy-Item "$workspace\archive.html" "$repoRoot\archive.html" -Force
    Write-Host "✓ Archive → archive.html"

git add -A
git commit -m "feat: $date AI daily brief (auto-pushed by Mavis cron)"
git push origin main

# ============ Step 5: 验证部署 (Cloudflare 通常 30-60s 内自动部署) ============
Start-Sleep -Seconds 20
$rootUrl = "https://daily-ai-2o3.pages.dev/"
$rootContent = (Invoke-WebRequest -Uri $rootUrl -UseBasicParsing -MaximumRedirection 10 -TimeoutSec 20).Content
$portalCheck = $rootContent | Select-String -Pattern '今日已推送\s*·\s*(\d{4}-\d{2}-\d{2})' -AllMatches
if ($portalCheck.Matches[0].Groups[1].Value -eq $date) {

$archiveStatus = (Invoke-WebRequest -Uri "https://daily-ai-2o3.pages.dev/ai-daily/$date/" -UseBasicParsing -MaximumRedirection 10 -TimeoutSec 15).StatusCode

} else {

### 9.5 archive.html / briefs.html 同步规则（2026-07-06 v6.3 新增）

**触发条件**：每天 cron deploy 时,生成新一期简报后,必须同步更新往期归档页面。

**核心原则**：**制作往期页面时,从仓库拉参考页面,然后依照参考页面制作更新**。

**来源 / 目标**：
- **参考模板（参考页面）**:`repo/example/archive.html`（简洁版样式,110 行,浅灰底 + 蓝色 accent + 金色日期）
- **生成目标 1（用户实际访问路径）**:`repo/briefs.html`（物理文件,绕开 Cloudflare Pages auto-trailing-slash 308）
- **生成目标 2（向后兼容路径）**:`repo/archive.html`（物理文件,但访问会被 308 → portal,仅作历史备份）

**操作步骤**（必走,无跳过）：

```

**FAQ**：
- Q: 为什么不更新 archive.html 路径,而是 briefs.html?
  A: Cloudflare Pages auto-trailing-slash 308 把 /archive.html → /archive → SPA fallback → portal 首页。briefs.html 是物理文件名,Cloudflare trailing-slash 不影响已知物理文件,308 → /briefs → 物理文件 → 200 serve。
- Q: archive.html 既然访问不到,为什么还要保留?
  A: 向后兼容（历史链接、SEO 缓存）和作为 reference template 的源。
- Q: cron 如果只更新 archive.html 不更新 briefs.html 会怎样?
  A: 用户从简报点"往期目录"按钮(/briefs.html)跳到 briefs.html,看不到新一期。**两个文件必须同步**。

**FAQ**：
- Q: 用户访问 `https://daily-ai-2o3.pages.dev/` 看到的是 portal 还是简报?
  A: **应该是 portal**(2 个入口)。如果看到简报内容,说明你错误地把简报 HTML 覆盖到了根 index.html。要从 portal-template.html 重新生成。

  A: 检查 cron 是否成功跑完 deploy 步骤;如果没有,手动执行 deploy 脚本。如果 deploy 成功但 portal 还停在昨天,可能是 portal-template.html 本身就有问题(用 git log 看 portal 历史)。
- Q: 往期 ai-daily/2026-07-01/index.html 被覆盖了?
